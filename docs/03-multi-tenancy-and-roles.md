# 03 — Multi-Tenant Strategy, Users and Roles

## Tenancy model

**Shared database, shared schema, row-level isolation** with an `organisation_id` column on every tenant-owned table, enforced by:

1. Application-layer scoping (repositories always filter by `ctx.organisationId`), **and**
2. PostgreSQL Row-Level Security policies on every tenant table, using a per-transaction session setting.

Both layers are mandatory. The application layer gives good error messages and performance; RLS is the backstop that makes a forgotten `WHERE` clause a *no rows* bug instead of a data breach.

```text
Platform (one database, one schema)
   │
   ├── Organisation A  (organisation_id = A)
   │      ├── Memberships (users ↔ org, with role)
   │      ├── Contacts, Companies, Leads, Opportunities
   │      ├── Pipelines, Stages, Lead statuses
   │      ├── Activities, Tasks, Tags, Custom field definitions
   │      ├── Audit log, Outbox, Exports
   │      └── Settings, Plan / entitlements
   ├── Organisation B  (organisation_id = B)
   └── Organisation C  (organisation_id = C)

Users are global (one identity) and may hold memberships in several organisations.
```

Why not schema-per-tenant or database-per-tenant: operational cost (migrations × N), connection pooling limits on serverless hosting, and no real security gain over RLS for this scale. Revisit only if a customer contractually requires physical isolation (see risks).

## Tenant identification

| Surface | Mechanism |
|---|---|
| Web app | URL segment `/{orgSlug}/…`. The slug is resolved to `organisation_id` and the user's membership is verified on every request. The "current organisation" is **never** taken from a cookie alone. |
| Server Actions | Receive `orgSlug` implicitly from the route; re-verify membership; build `TenantContext`. |
| Public API (future) | API key → `organisation_id`. Keys are tenant-bound; they cannot name another tenant. |
| Background jobs | Job payload carries `organisation_id`; the worker opens `withTenant` for that id. Jobs never process multiple tenants in one transaction. |
| Webhooks in (future) | Provider identifier maps to a stored integration row that belongs to exactly one organisation. |

## Tenant ownership

- Each organisation has exactly one **Owner** (a membership with role `owner`). Ownership can be transferred by the owner to another admin; the transfer is audited.
- The owner cannot be removed or demoted except through transfer.
- An organisation's `created_by_user_id` is retained for audit but is not the authority; the owner membership is.

## User membership

- `users` is a platform-level table (not tenant-scoped). Identity = verified email.
- `memberships (user_id, organisation_id, role, status)` links users to organisations. Unique on `(user_id, organisation_id)`.
- **Users can belong to multiple organisations.** This is required for consultants, agencies, accountants and the product team's own testing. Cost is low: an organisation switcher in the UI and membership verification per request, which is needed anyway.
- Only one organisation is *active* per request (from the URL). There are no cross-organisation views.
- Invitations: `invitations (organisation_id, email, role, token_hash, expires_at, invited_by)`. Accepting an invitation creates the membership; a user who already exists simply gains a membership.

## Tenant-scoped database queries

The `withTenant` helper is the single entry point to the database for tenant data:

```ts
withTenant(ctx, async (tx) => {
  // inside: SET LOCAL app.current_org = ctx.organisationId
  //         SET LOCAL app.current_user = ctx.userId
  //         SET LOCAL ROLE crm_app   (non-bypass role)
  return tx.select().from(contacts).where(eq(contacts.organisationId, ctx.organisationId));
});
```

RLS policy pattern (applied to every tenant table, generated by a migration helper so none can be missed):

```sql
ALTER TABLE contacts ENABLE ROW LEVEL SECURITY;
ALTER TABLE contacts FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON contacts
  USING (organisation_id = current_setting('app.current_org')::uuid)
  WITH CHECK (organisation_id = current_setting('app.current_org')::uuid);
```

A CI check asserts that every table with an `organisation_id` column has RLS enabled and forced.

## Authorisation model

Roles are **organisation-wide** (no record-level sharing in MVP). Four roles:

| Capability | Owner | Admin | Manager | Member |
|---|---|---|---|---|
| View all CRM records in the organisation | ✔ | ✔ | ✔ | ✔ |
| Create contacts, companies, leads, opportunities, activities, tasks | ✔ | ✔ | ✔ | ✔ |
| Edit records they own | ✔ | ✔ | ✔ | ✔ |
| Edit records owned by others | ✔ | ✔ | ✔ | ✖ (configurable per org: "members can edit all records", default off) |
| Reassign owner of a record | ✔ | ✔ | ✔ | ✖ |
| Delete (soft) records | ✔ | ✔ | ✔ | Own records only |
| Restore / permanently delete | ✔ | ✔ | ✖ | ✖ |
| Bulk operations (bulk edit, bulk delete, merge duplicates) | ✔ | ✔ | ✔ | ✖ |
| Export CSV | ✔ | ✔ | ✔ | ✖ (configurable, default off) |
| Import CSV | ✔ | ✔ | ✔ | ✖ |
| Manage pipelines, stages, lead statuses, custom fields, tags | ✔ | ✔ | ✖ | ✖ |
| Invite users, change roles (below their own), remove users | ✔ | ✔ | ✖ | ✖ |
| View audit log | ✔ | ✔ | ✖ | ✖ |
| Manage integrations, API keys, webhooks (future) | ✔ | ✔ | ✖ | ✖ |
| Billing, plan changes (future) | ✔ | ✖ | ✖ | ✖ |
| Rename organisation, data export (whole organisation), delete organisation, transfer ownership | ✔ | ✖ | ✖ | ✖ |

Implementation: a single `permissions.ts` with a `can(ctx, action, resource?)` function and a static role → actions map, plus the two org-level toggles. Services call `can` before any write. UI uses the same function to hide controls, but the service check is authoritative.

Deliberately **not** in MVP: custom roles, per-team visibility, record-level sharing, field-level permissions. The `role` column is a string enum so custom roles can be introduced later by adding a `roles` table without migrating existing data.

## Cross-tenant protection

Threats and controls:

| Threat | Control |
|---|---|
| Forgotten `WHERE organisation_id` | RLS backstop; isolation test suite |
| ID guessing across tenants (IDOR) | Every lookup by id is also scoped by `organisation_id`; RLS; UUIDv7 ids |
| Client supplies `organisationId` in payload | Payload schemas do not include `organisationId`; it is always taken from `TenantContext` |
| Foreign key to another tenant's row (e.g. contact → company in org B) | Composite checks: services verify referenced rows exist *in this tenant*; RLS makes the cross-tenant row invisible so the FK lookup fails; additionally, composite FKs `(organisation_id, company_id)` on the most sensitive links |
| Cached data leaking between tenants | Cache keys always include `organisation_id`; no shared in-memory caches of tenant data in serverless runtime |
| Search index leakage | Search is Postgres full-text within the same RLS-protected tables; no external index in MVP |
| Background job processing wrong tenant | Jobs carry `organisation_id`; `withTenant` per job; job tables themselves are tenant-scoped |
| Super-admin misuse | Separate `platform_admins` table; separate code path; every access is audited with reason; break-glass sessions time-limited (see security doc) |
| Log leakage | Logs contain ids, never record content; PII scrubbing in error reporting |

## Audit requirements

`audit_log (id, organisation_id, actor_user_id, actor_type[user|system|api_key|platform_admin], action, entity_type, entity_id, before jsonb, after jsonb, metadata jsonb, request_id, ip, user_agent, created_at)`

- Every create / update / delete / restore / export / login / role change / settings change writes a row, inside the same transaction as the change.
- Append-only: the application role has INSERT and SELECT only; no UPDATE/DELETE grant.
- Retention: configurable per plan; default 12 months rolling, minimum 90 days.
- Visible to owners and admins in Settings → Audit log, filterable by user, entity, action, date.

## Deletion requirements

Two levels:

1. **Record deletion (soft):** `deleted_at` + `deleted_by`. Excluded from all queries by default via a repository-level filter. Restorable for 30 days from a "Recently deleted" screen, then hard-deleted by a scheduled job. Child records: activities and tasks of a soft-deleted contact remain but are hidden with their parent; opportunities are not cascaded (they are deliberately re-parented or deleted explicitly).
2. **Organisation deletion:** owner-initiated, requires re-authentication and typing the organisation name. Organisation enters `deletion_scheduled` state for 14 days (login blocked for non-owners, banner for owner, cancellable). After the grace period a job hard-deletes all tenant rows in dependency order and writes a platform-level tombstone (organisation id, deletion time, no content). Backups age out naturally (see privacy doc).

Data subject deletion (GDPR erasure of one contact) is the soft delete followed by immediate hard delete on request, plus anonymisation of that contact's references in audit rows (`before`/`after` payload fields replaced with `[erased]`).

## Export requirements

- **Per-entity CSV export** from any list view (respecting current filters) — MVP.
- **Whole-organisation export** (all entities as CSV in a zip, plus JSON) generated by a background job, downloadable via signed, expiring link, audited — MVP (required for portability and GDPR).
- **Per-contact data subject export** (all data about one person as JSON) — MVP, since it costs little once the above exist.
- Exports are stored in object storage under a tenant-prefixed key and deleted after 7 days.
