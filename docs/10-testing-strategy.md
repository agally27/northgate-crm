# 10 — Testing Strategy

## Constraints from the audit

- Docker is not installed, so database tests run against the **local PostgreSQL 17** (Confirmed) using a disposable database per test run (`crm_test_<runid>` created from a template database that already has migrations applied). CI uses the `postgres:17` service container in GitHub Actions. If Docker is installed later, Testcontainers becomes an option behind the same helper.
- No existing tests or frameworks; all proposed.

## Layers

| Layer | Tool | Scope | Runs |
|---|---|---|---|
| Unit | Vitest | Pure logic: validation schemas, permissions map, money/phone/email normalisation, duplicate scoring, RRULE handling, filter → query builders, dashboard maths | every commit, < 30 s |
| Integration (service + DB) | Vitest + real Postgres, one transaction per test rolled back | Services and repositories with real RLS, constraints and triggers | every commit |
| Database | Vitest + SQL assertions | Migrations apply from empty and from previous release; RLS policy coverage; role privileges (`crm_app` has no BYPASSRLS, no DDL, INSERT-only on audit_log); constraint behaviour; index presence for documented queries (`EXPLAIN` guards on hot paths) | every commit |
| API | Vitest + supertest-style fetch against Route Handlers; later OpenAPI contract tests | Auth handlers, internal endpoints, `/api/v1` when built | every commit |
| UI component | Vitest + Testing Library | Form validation display, list filters, timeline grouping, board keyboard interaction | every commit |
| E2E | Playwright (Chromium, WebKit; mobile viewport project) | Primary journeys per phase; axe accessibility checks | on PR and nightly |
| Authentication | Integration + E2E | Sign-up/verify/sign-in/reset/magic link/invitation; throttling; session revocation; cookie flags | every commit |
| Authorisation | Integration matrix | For each role × each service action, expected allow/deny from the permissions table in `03` — generated table test so the doc and code cannot drift | every commit |
| Tenant isolation | Dedicated suite `tests/isolation/` (see `06` list of 9 tests) | Blocks merge; runs on every commit; also nightly against production-like data volume | every commit + nightly |
| Regression | Whole suite + a curated E2E smoke pack tagged `@smoke` | On every PR; smoke on deploy to preview and production | continuous |
| Performance | k6 (HTTP) + Playwright timing; seeded dataset of 1 org × 50k contacts / 10k opportunities / 500k activities plus 200 small orgs | Budgets: list p95 < 300 ms server time, detail p95 < 400 ms, dashboard p95 < 500 ms, search p95 < 200 ms, board load < 600 ms with 500 open opportunities | nightly and before each release |
| Security | `pnpm audit`, CodeQL, Semgrep rules (raw SQL, missing `withTenant`, handler reading `organisationId` from input), ZAP baseline scan on preview, header checks; external pen test before launch | CI + pre-launch |

## Test data and fixtures

- Factory functions per entity (`makeContact(ctx, overrides)`) that always insert via the service layer so tests exercise the real path.
- Two standard organisations (`orgA`, `orgB`) with mirrored data seeded in every integration test, so isolation assertions are cheap to add anywhere.
- Deterministic clock injection through `ctx.now()`.

## Acceptance criteria per milestone

Listed per phase in `09-mvp-and-roadmap.md`. In addition, each phase must add:

- ≥ 1 E2E journey.
- Isolation tests for every new tenant table (generated by registering the table in the isolation matrix; the policy coverage test fails if a table is unregistered).
- Authorisation matrix rows for every new action.

## CI pipeline (GitHub Actions, proposed)

1. Install (pnpm, frozen lockfile) → typecheck → lint → unit.
2. Start Postgres 17 service → migrate template → integration + database + authorisation + isolation suites.
3. Build → Playwright E2E (sharded) → axe.
4. Security scans.
5. Deploy preview (Vercel) → smoke pack against preview.
Merge is blocked on 1–4; deploy to production is blocked on 5.
